# Cloudflare D1 as a remote backend for ito

**Researched:** 2026-08-24 · scenario: one user, a Mac in São Paulo, a VPS in the United States, occasional offline periods on a network that blocks VPN/Tailscale but not plain HTTPS, never two machines writing at the same moment.

This note answers whether ito's optional cloud backend (decision [0004](../adr/0004-optional-cloud-backend.md)) could or should move from Turso to Cloudflare D1. Every factual claim below carries a link to a primary source — Cloudflare docs, the Cloudflare changelog, Turso docs, or the relevant GitHub repository. Where a number is an estimate rather than a published figure, it says so.

## 1. What D1 is, and whether ito's SQL runs on it

D1 is Cloudflare's serverless SQL database built on SQLite; it went generally available in April 2024, and alpha databases were deprecated in favor of the GA architecture ([release notes](https://developers.cloudflare.com/d1/platform/release-notes/), [Building D1: a Global Database](https://blog.cloudflare.com/building-d1-a-global-database/)). Cloudflare does not publish which SQLite version D1 tracks — the [SQL statements page](https://developers.cloudflare.com/d1/sql-api/sql-statements/) and the release notes contain no version entry, so **that fact could not be sourced** and should not be assumed.

The compatibility surface is described positively rather than as a list of exclusions: D1 states it is "compatible with most SQLite's SQL convention" and enumerates the extensions it ships — the [FTS5 module](https://www.sqlite.org/fts5.html) for full-text search including `fts5vocab`, the JSON extension, and math functions ([SQL statements](https://developers.cloudflare.com/d1/sql-api/sql-statements/)). The PRAGMA whitelist is explicit and short: `table_list`, `table_info`, `table_xinfo`, `index_list`, `index_info`, `index_xinfo`, `quick_check`, `foreign_key_check`, `foreign_key_list`, `case_sensitive_like`, `ignore_check_constraints`, `legacy_alter_table`, `recursive_triggers`, `reverse_unordered_selects`, `foreign_keys`, `defer_foreign_keys`, `optimize` — and "D1 PRAGMA statements only apply to the current transaction" ([same page](https://developers.cloudflare.com/d1/sql-api/sql-statements/)).

Checking ito's schema and queries against that surface, `internal/store/store.go` uses: a plain relational schema with composite foreign keys and a `CHECK` constraint (`migrateV1`, line 686); `ALTER TABLE ... ADD COLUMN` (`migrateV2`, `migrateV3`, `migrateV4`); `PRAGMA table_info(...)` inside `columnExists` (line 792); one non-recursive CTE (`WITH batch_members AS ...`, line 1413); no triggers, no window functions, no `RETURNING`, no `ATTACH`; and an FTS5 external-content virtual table `issues_fts` with `content='issues'`, `tokenize='unicode61'`, `prefix='2 3 4'`, queried through `MATCH` and ranked with `bm25(issues_fts)` (lines 709, 2337, 2407). All of that is inside D1's documented surface: `PRAGMA table_info` is whitelisted, FTS5 is a supported extension, and the local-only DSN settings (`_txlock=immediate`, `journal_mode(WAL)`, `busy_timeout(5000)`) are already skipped on the cloud path — `openBackend` (line 559) applies them only in `BackendLocal`.

Two problems remain, and they are the important ones.

**Transactions.** D1 has no interactive transaction. The Worker API documents that "D1 operates in auto-commit" and that batched statements are the transaction unit: "Batched statements are SQL transactions. If a statement in the sequence fails, then an error is returned for that specific statement, and it aborts or rolls back the entire sequence" ([D1Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)). The foreign-key page states the same thing from the other side: "D1 runs every query inside an implicit transaction, user queries cannot change this during a query or migration" ([Foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)). Sending your own `BEGIN TRANSACTION` produces "cannot start a transaction within a transaction" — the import guide tells you to strip `BEGIN TRANSACTION`/`COMMIT` from dumps for exactly that reason ([Import and export data](https://developers.cloudflare.com/d1/best-practices/import-export-data/)). ito calls `db.Begin()` in roughly fourteen places (`Migrate` at line 651 and every mutating store method: 1027, 1062, 1092, 1159, 1202, 1674, 1756, 1795, 1872, 2045, 2065, …), and several of them are genuinely read-then-write inside one transaction — allocating `projects.last_id` before inserting an issue, or reading the current title/body to emit the FTS5 `'delete'` row before re-inserting (lines 2001–2004). On D1 those would have to be rewritten as pre-composed batches, which is not a mechanical change: a batch cannot branch on a value it read earlier in the same batch. This is the single largest piece of work in a D1 migration, and it is a change to the store's internals rather than to its edges.

**FTS5 and backups.** D1 supports FTS5 at query time, but "export is not supported for virtual tables, including databases with virtual tables… As a workaround, delete any virtual tables, export, and then recreate virtual tables" ([Import and export data](https://developers.cloudflare.com/d1/best-practices/import-export-data/)). The underlying bug is worse than the docs let on: [cloudflare/workers-sdk#9519](https://github.com/cloudflare/workers-sdk/issues/9519), open since 2025-06-07 and last touched 2026-08-17, reports that attempting to export a database containing fts5 tables leaves the database permanently erroring on every query and unloadable in the dashboard. ito's `issues_fts` is exactly such a table. Meaning: on D1, ito's cloud database would not be exportable without first dropping and rebuilding the search index, and the naive attempt is a documented way to brick it.

## 2. Where the data physically sits

A D1 database has one primary instance in one location, and "D1 request latency is dependent on the physical proximity of a user to the primary database instance" ([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)). You steer that placement with a location hint at creation time, and the available hints are `wnam`, `enam`, `weur`, `eeur`, `apac`, `oc`. The docs are explicit about the gap that matters here: "D1 location hints are not currently supported for South America (`sam`), Africa (`afr`), and the Middle East (`me`)" ([Data location](https://developers.cloudflare.com/d1/configuration/data-location/)). Absent a hint, "D1 will automatically create your primary database instance in a location close to where you issued the request to create a database", and even with a hint, "providing a location hint does not guarantee that D1 runs in your preferred location. Instead, it will run in the nearest possible location (by latency) to your preference" ([same page](https://developers.cloudflare.com/d1/configuration/data-location/)). So there is no way to put a D1 primary in Brazil.

Read replication exists and would in principle help a reader far from the primary, but it does not help this scenario. It entered public beta on 2025-04-10 and the docs still link to the [beta blog post](https://blog.cloudflare.com/d1-read-replication-beta/) without declaring GA ([release notes](https://developers.cloudflare.com/d1/platform/release-notes/), [changelog](https://developers.cloudflare.com/changelog/post/2025-04-10-d1-read-replication-beta/)). Replicas are created "in every supported region" — the same six: ENAM, WNAM, WEUR, EEUR, APAC, OC — so again no South America. Writes are never served locally: replicas "forward any write queries to the primary database instance". And decisively for ito, "Sessions API is only available via the D1 Worker Binding and not yet available via the REST API" ([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)). A Go CLI talking to the REST API cannot use replicas at all; only a Worker can.

On expected latency, Cloudflare publishes no per-region figures, so the numbers below are measured or estimated, and labelled as such. Measured from this Mac in São Paulo on 2026-08-24 with `curl`: TLS handshake to `api.cloudflare.com` completes in about 30 ms and the connection terminates at the GRU colo (`https://api.cloudflare.com/cdn-cgi/trace` returns `colo=GRU`, `loc=BR`); a `cdn-cgi/trace` response, served entirely at the edge, has a time-to-first-byte of 39–50 ms; a `POST` to the D1 `/query` path with an invalid account, rejected by authentication at the edge, returns in 57–65 ms. That last number is the floor, not the query latency — it never reached a database. Since May 2025 D1 authenticates REST requests at the nearest Cloudflare data center instead of proxying to the US core, an improvement Cloudflare puts at "50-500 ms depending on request location and database location", with "requests and databases outside the United States see a bigger benefit" ([changelog, 2025-05-30](https://developers.cloudflare.com/changelog/2025-05-30-d1-rest-api-latency/)). By contrast, an authenticated control-plane call from the same machine (`/client/v4/user/tokens/verify`, which still round-trips to the core) took 366–398 ms — a useful illustration of what a São Paulo→US-core round trip costs.

**Estimate, not a published figure:** with the primary hinted to `enam`, one D1 REST query from São Paulo should land somewhere around 150–250 ms end to end — roughly the ~60 ms edge leg plus a GRU→US-east round trip on Cloudflare's backbone plus D1's own execution time. From the US VPS, with the primary in `enam`, expect roughly 30–80 ms. These are inferred from the measurements above and the shape of the system, not measured against a real D1 database; anyone deciding on this should create a throwaway D1 database and time it.

Compare that to the numbers already in hand for ito's current Turso backend at `aws-us-east-2`: ~390 ms TCP connect from São Paulo versus 36 ms to `sa-east-1`. D1 would very likely be *faster* than today's Turso setup from Brazil, because the TLS handshake terminates at GRU rather than in Ohio. It would still not be fast.

## 3. Reaching D1 from a Go program outside Workers

Three routes exist, and none is comfortable.

**The built-in REST API.** The endpoint is `POST /accounts/{account_id}/d1/database/{database_id}/query` (and a performance-oriented `/raw` variant that returns rows as arrays instead of objects), authenticated with `Authorization: Bearer {token}` on an API token holding D1 Read or D1 Write ([Cloudflare API — D1 query](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/)). Each call is one HTTPS round trip. Cloudflare's own guidance is the thing to weigh: "D1's built-in REST API is best suited for administrative use as the global Cloudflare API rate limit applies" ([Build an API to access D1 using a proxy Worker](https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/)). That global limit is "1,200 requests per five minute period per user, and applies cumulatively regardless of whether the request is made via the dashboard, API key, or API token" ([API rate limits](https://developers.cloudflare.com/fundamentals/api/reference/limits/)) — four requests per second, shared with everything else you do with that account. The docs stop short of saying "not for production", but "best suited for administrative use" plus a 4 rps account-wide ceiling is the same warning in politer language. For a single-user CLI it is probably survivable; for a TUI that fires several concurrent queries per refresh (ito already sets `maxIdleConns = 16` for exactly that burst, line 292) it is uncomfortably close to the line.

**A thin Worker proxy.** Cloudflare's recommended alternative, and the only way to get the Sessions API and read replicas ([tutorial](https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/), [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)). It removes the account rate limit, keeps the token out of the client, and lets you implement a real batch endpoint. It also means ito acquires a deployed service, a second language, and a deployment pipeline — which decision 0004 explicitly rejected: "A backend service in front of the database. Unnecessary: the CLI can hold the connection itself."

**Go drivers.** Several exist on GitHub; none is official and none is healthy. [`peterheb/cfd1`](https://github.com/peterheb/cfd1) (v0.3.14, last pushed 2025-03-03, 4 stars) is the most honest about the constraint: "this driver does not support transactions through `db.Begin()`, as connections to D1 over the REST API are not persistent — every query creates a new HTTP round-trip to the API and connection" ([pkg.go.dev](https://pkg.go.dev/github.com/peterheb/cfd1)). [`SyneHQ/d1_go_sql`](https://github.com/SyneHQ/d1_go_sql) (7 stars, last pushed 2025-12-22) advertises a `database/sql` driver; [`crosleyzack/cloudflare-d1-go`](https://github.com/crosleyzack/cloudflare-d1-go) (0 stars) and [`ashayas/cloudflare-d1-go`](https://github.com/ashayas/cloudflare-d1-go) (6 stars, last pushed 2024-11-16) are thin REST wrappers, not drivers. The official [`cloudflare-go`](https://pkg.go.dev/github.com/cloudflare/cloudflare-go/v3/d1) SDK covers D1 management and query calls but is not a `database/sql` driver. So `store.New(db *sql.DB)` could be fed a D1 driver, but not one that honors `db.Begin()` — which is the whole point of the seam for ito's writes.

## 4. Free tier and pricing

D1's Workers Free plan allows 5 million rows read per day, 100,000 rows written per day, and 5 GB total storage; Workers Paid includes the first 25 billion rows read and 50 million rows written per month, then charges $0.001 per million rows read, $1.00 per million rows written, and $0.75 per GB-month beyond the first 5 GB included ([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)). Billing is by rows *scanned*, not rows returned: "D1 bills by the number of rows read and rows written, not by the number of rows your query returns" ([Use indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/)).

The structural limits worth knowing: maximum database size 10 GB on Paid and 500 MB on Free; maximum SQL statement 100 KB; maximum query duration 30 seconds; maximum 100 bound parameters per query; maximum 100 columns per table; maximum row/string/BLOB 2 MB; queries per Worker invocation 1,000 on Paid and 50 on Free; maximum LIKE/GLOB pattern 50 bytes ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)). For a single-user issue tracker, none of these bind — ito's database is measured in megabytes and its query volume in hundreds per day. **D1's free tier is comfortably sufficient for this scenario.** The 100-bound-parameter cap is the only one worth a second look, since ito builds batched inserts during backend migration.

## 5. Comparison

Before the table, one correction to the premise. **Turso cannot be relocated to São Paulo.** Turso announced it is "moving fully to AWS", migrating free-tier users off the old Fly.io footprint ([Upcoming changes to the Turso Platform and Roadmap](https://turso.tech/blog/upcoming-changes-to-the-turso-platform-and-roadmap)), and the documented location set is six AWS regions: `aws-ap-northeast-1` (Tokyo), `aws-ap-south-1` (Mumbai), `aws-eu-west-1` (Ireland), `aws-us-east-1` (Virginia), `aws-us-east-2` (Ohio), `aws-us-west-2` (Oregon) ([List Locations](https://docs.turso.tech/api-reference/locations/list)). There is no `sa-east-1` and no São Paulo. The 36 ms figure measured against `sa-east-1` describes a region Turso does not offer. Caveat on this one: that list comes from the API reference, and `turso db locations` is the authoritative live answer — worth running before acting, though the AWS-only migration blog corroborates it.

Turso's free plan gives 100 databases, 5 GB storage, 500 million rows read per month, 10 million rows written per month, and 3 GB of syncs; Developer is $4.99/month, Scaler $24.92/month ([Turso pricing](https://turso.tech/pricing)). Turso Cloud's own SQLite caveats are minor for ito and already handled: `PRAGMA busy_timeout` and `PRAGMA journal_mode` are unsupported, `user_version` and `application_id` are read-only, and the recommended migration-tracking pattern is a version *table* — which is what ito's `schema_version` table already is ([Turso Cloud limitations](https://docs.turso.tech/cloud/limitations)).

For the local-first-plus-sync column, the relevant development is that Turso now ships a first-party Go sync driver. `turso.tech/database/tursogo` (v0.7.2, published 2026-07-30) registers a `database/sql` driver, requires no CGO — "this driver uses the awesome purego library to call C (in this case Rust with C ABI) functions from Go" — and exposes explicit `push()`/`pull()` sync against a Turso Cloud remote, with "last push wins" conflict resolution on logical statements ([Go quickstart](https://docs.turso.tech/sdk/go/quickstart), [sync usage](https://docs.turso.tech/sync/usage), [pkg.go.dev](https://pkg.go.dev/turso.tech/database/tursogo)). That is very close to exactly what this scenario wants, and it would give ito local-speed reads and writes with an explicit sync step. The catch is severe and specific: the new Turso engine does not implement SQLite FTS5. Its compatibility matrix lists "SQLite FTS3/FTS4/FTS5 — ❌ No — Use Turso FTS instead", because "Turso implements FTS using Tantivy instead of SQLite's FTS3/FTS4/FTS5" ([COMPAT.md](https://github.com/tursodatabase/turso/blob/main/COMPAT.md)). ito's `issues_fts` table, its `MATCH` filter, and its `bm25()` ranking would all have to be rewritten against Turso's own FTS, and the local backend (`modernc.org/sqlite`) would then diverge from the synced one — which breaks the property that made decision 0004 cheap in the first place. The older `go-libsql` embedded-replica driver keeps FTS5 (libSQL is a SQLite fork) but is the CGO-based path; only `libsql-client-go` (remote only, no local file) and `tursogo`/`tursogo-serverless` are pure Go ([Go quickstart](https://docs.turso.tech/sdk/go/quickstart)).

| | Cloudflare D1 (REST, primary in `enam`) | Turso Cloud (libSQL, `aws-us-east-1/2`) — today's setup | Local-first + sync |
|---|---|---|---|
| Latency from São Paulo | ~150–250 ms/query (estimate; edge terminates at GRU in ~60 ms, measured) | ~390 ms TCP connect measured; every query pays a full BR↔US round trip | sub-millisecond; network cost only on an explicit sync |
| Latency from the US VPS | ~30–80 ms/query (estimate) | tens of ms; same continent as the primary | sub-millisecond, same as above |
| Works offline | No | No | Yes — that is the point |
| Transactions | No `db.Begin()`; batch-only, and no Go driver that honors `sql.Tx` | Works today; interactive transactions over the HTTP driver are limited (already noted in ADR 0004) | Full local `sql.Tx` |
| FTS5 | Supported for queries, but the database becomes unexportable and export attempts can brick it ([#9519](https://github.com/cloudflare/workers-sdk/issues/9519)) | Supported (libSQL is a SQLite fork) | `tursogo`: **not** supported — rewrite search against Tantivy FTS. `go-libsql`: supported, but CGO |
| Change in ito | Large: rewrite ~14 `db.Begin()` sites into pre-composed batches, add a D1 driver (none official, none maintained), or stand up a Worker proxy | None — this is the current code | Medium with `tursogo` if search is rewritten; large if a custom sync layer is built by hand |
| Cost per month | $0 (free tier is ample for this workload) | $0 (free tier is ample) | $0 on Turso's free tier; a hand-rolled sync costs implementation time instead |

## 6. Recommendation

**Do not move ito to Cloudflare D1.** The case against it is not about limits or price — the free tier is generously sized for a single-user tracker and the structural caps are nowhere near binding. It is about two hard incompatibilities and one absent capability. D1 has no interactive transaction, and ito's store is built on `db.Begin()` with read-then-write logic inside the transaction; converting that to batches is not a translation, it is a redesign of the store's write path, and the only Go drivers available are unofficial, near-unmaintained, and honest about not supporting `sql.Tx`. D1 also cannot back up a database containing an fts5 virtual table, and the attempt has been reported for over a year to leave the database permanently broken. Finally, D1 cannot put a primary anywhere in South America, and its read replication — the one mechanism that could have compensated — is still in public beta and reachable only from a Worker binding, which is exactly the middle tier decision 0004 deliberately refused. You would pay a real rewrite for a backend that is faster than today from Brazil but still remote, still online-only, and worse in backup safety.

**Also drop the idea of relocating Turso to São Paulo** — it isn't on offer. Turso is AWS-only now, and its six regions stop at Virginia. The 36 ms to `sa-east-1` is a measurement of a region no candidate provider actually sells you. This matters because it removes the cheapest possible fix — "same setup, closer region" — from the table entirely. Every remaining option is either "accept a US round trip" or "stop making the network part of the read path".

**What the scenario actually argues for is local-first.** Read the constraints again: one user, never two simultaneous writers, sometimes offline, on a network that permits plain HTTPS. That is not a distributed-database problem; it is a replication problem with the hard part — write conflicts — removed by assumption. The current architecture pays a full São Paulo→Ohio round trip on every keystroke-adjacent query in the TUI, and gets nothing back for it, because there is no concurrency to arbitrate. A local database with an explicit push/pull sync makes every read and write instant on both machines, works on the university network and on a plane, and confines the network to a step the user chooses to run.

The tempting implementation is `turso.tech/database/tursogo`: pure Go, `database/sql`, first-party push/pull, free tier, and it drops straight into the `New(db *sql.DB)` seam. The honest blocker is FTS5. ito's search is an external-content fts5 index with `bm25()` ranking, and the new Turso engine replaced FTS5 with a Tantivy-backed implementation. Adopting `tursogo` therefore means rewriting search, and — worse — it means the local backend and the synced backend would no longer share a dialect, which is precisely the property that made decision 0004 a small change. The libSQL embedded-replica path (`go-libsql`) keeps FTS5 but reintroduces CGO, which costs cross-compilation and build simplicity.

So the recommendation, in order of what I would actually do:

Stay on Turso as-is for now, and treat the ~390 ms as the known price of decision 0004 rather than something to fix by swapping providers — every swap available today is a downgrade or a rewrite. If the latency becomes intolerable (and in a TUI that refreshes on navigation, it plausibly will), the move worth designing is local-first sync, not a different remote. When you design it, the first question to settle is search: either accept a search rewrite and take `tursogo`'s sync for free, or keep fts5 and build a minimal sync yourself over the existing libSQL remote — an append-only change log plus a `push`/`pull` command pair, which for a single-writer, never-concurrent scenario is a genuinely small piece of code and keeps the dialect identical across both backends. The second option preserves everything decisions 0001 and 0004 bought and adds the one property they lack, which is why I would sketch it before reaching for anyone's sync engine.

The one thing not worth doing is spending the rewrite on D1.
